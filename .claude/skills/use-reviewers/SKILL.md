# Use Reviewers

Automatically launch independent code review agents with proper names, verdicts, and approval workflows.

## When to Use This Skill

Launch reviewers when you:
- **Create a PR** with non-trivial code changes (more than typo/config fixes)
- **Need independent verification** of correctness, security, or design decisions
- **Want defense-in-depth**: Each PR must be reviewed by at least 2 reviewers, each posting "Approval Recommended" before merge
- **Face ambiguous findings**: Reviewer comments are pertinent only if they identify real bugs, security issues, or critical design flaws — nits and style preferences are skippable
- **Must respond to comments**: Always reply on the PR thread explaining why each comment is addressed or declined

## Launch Pattern

For each PR requiring review:

```
1. Create the PR with clear description
2. Assign reviewers based on change type:
   - API/Core Logic → Dr. Alice + Marcus
   - Frontend UI → Evan + Dr. Priya  
   - Backend/Data → Sam + Marcus
   - Full Stack → Dr. Alice + Marcus (or all 3 for critical)
3. Each reviewer posts independent review with:
   - Detailed findings with line numbers
   - Verdict: "Approval Recommended" ✓ or "Changes Requested" ✗
   - Attribution footer
4. Respond to each comment on PR thread:
   - If pertinent → fix and push new commit
   - If not pertinent → explain why in thread
5. Merge only after both reviewers post "Approval Recommended"
```

## Review Prompt for Each Reviewer

Use this exact prompt when launching reviewer agents:

---

### **Code Review Briefing**

You are **{REVIEWER_NAME}**, an expert code reviewer focused on **{FOCUS_AREA}**.

Your task: Review this pull request comprehensively and independently. Respond with real findings only.

#### Instructions

1. **Fresh Read**: Read the full PR diff from scratch. Don't skim.

2. **Real Findings Only**: Report only verifiable issues:
   - **{FOCUS_AREA} Issues**: [Insert specific focus]
   - Correctness bugs (logic errors, type mismatches, missing validations)
   - Security vulnerabilities (injection, encoding, sanitization gaps)
   - Performance issues (only if severe, not micro-optimizations)
   - Missing test coverage (only critical paths)

3. **For Each Finding**:
   ```
   File: path/to/file.ts:LINE
   Summary: One sentence stating the defect
   Scenario: Concrete inputs → wrong output/crash
   Verdict: CONFIRMED (read in code) or PLAUSIBLE (needs verification)
   ```

4. **Inline Comments**: When reporting issues, show the problematic code and explain why it's wrong.

5. **Final Verdict**: At the end, state clearly:
   - **"Approval Recommended"** ✓ if findings are minor/fixed or none exist
   - **"Changes Requested"** ✗ if blocking issues remain unfixed
   - **"Needs Further Review"** ? if uncertain about severity

6. **Attribution Footer**:
   ```
   
   ---
   _Generated by [Claude Code](https://claude.ai/code)_
   ```

#### Context
- Repository: {REPO_NAME}
- PR: #{PR_NUMBER}
- Branch: {BRANCH_NAME}
- Changed files: {FILE_LIST}
- Your role: {REVIEWER_NAME} ({FOCUS_AREA})

Read the full diff, then post your findings as a review comment on GitHub.

## Handling Reviewer Comments

When reviewers post findings:

1. **Assess Pertinence**:
   - Is this a real bug? → **Pertinent** ✓
   - Security issue? → **Pertinent** ✓
   - Design flaw? → **Pertinent** ✓
   - Style/formatting nit? → **Not pertinent** ✗
   - Over-engineering suggestion? → **Assess case-by-case** ?

2. **Respond in PR Thread**:
   ```
   For pertinent findings:
   "Good catch. Fixed in commit {HASH}. Changes: {BRIEF_DESC}"
   
   For non-pertinent findings:
   "Appreciate the suggestion, but this is a design choice 
   for {REASON}. Not fixing this round."
   ```

3. **Fix and Push**:
   - Create new commit for each fix
   - Use conventional commit format: `fix(scope): address reviewer comment`
   - Re-request review after pushing

4. **Merge Criteria**:
   - Both reviewers post "Approval Recommended" ✓
   - All pertinent comments addressed
   - CI passes on latest commit

## Example: Responding to Comments

**If Alice finds a type error:**
```
Reviewer: "Line 45: `toSeriesValues()` called twice 
unnecessarily. Should cache result."

Your PR response:
"✓ Fixed in commit abc123. Changed to cache in `rsiValues` 
variable per best practice."

Then: Create commit, push, re-request review
```

**If Marcus finds a non-issue:**
```
Reviewer: "Why not use const instead of let on line 22?"

Your PR response:
"This var is reassigned in the loop (line 25). 
Const would break this logic. ✗ Not fixing."
```

## Approval Matrix

| Scenario | Action |
|----------|--------|
| Both reviewers: "Approval Recommended" | **MERGE** ✓ |
| One: "Approval", One: "Changes Requested" | **HOLD** — Fix or respond |
| Both: "Changes Requested" | **HOLD** — Must fix |
| Either: "Needs Further Review" | **ESCALATE** — Add 3rd reviewer |
